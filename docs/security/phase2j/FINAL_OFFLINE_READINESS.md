## DNS / QEMU egress — offline analysis

QEMU's slirp user network exposes guest gateway 10.0.2.2 and guest DNS 10.0.2.3, but its **host-side resolver target** may come from the runner's resolver configuration. A 127.0.0.53 stub or private address can conflict with QEMU-owner OUTPUT rejects. The existing harness permits generic UDP/53 to public IPv4, but has **no TCP/53 fallback**. It permits any public TCP 80/443, not a domain allow list. Loopback ESTABLISHED TCP is an unexecuted conntrack hypothesis. IPv6 guest is disabled in future QEMU flags and host IPv6 reject is configured but no kernel enforcement has been probed.

Proposed fail-closed preflight **before guest creation**: obtain runner IPv4 resolver endpoint(s), distinguish host stub from QEMU's actual outbound resolver, reject unknown/loopback/private/link-local destinations unless a separately reviewed narrowly scoped resolver proxy is demonstrated; select one explicitly reviewed public IPv4 upstream and restrict QEMU-UID outbound UDP and TCP 53 to that address only; permit explicitly reviewed public bootstrap HTTPS/HTTP destinations as required (use named services, pin signed artifact/content checksums, never hardcode dynamic IPs); fail on egress deny mismatch; verify QEMU ownership/host forwards and no unexpected IPv6; a **kernel networking negative test** would need its own approval and is not included. DO NOT just add broad localhost allow or infer the effective resolver from `/etc/resolv.conf` text.

Source: https://www.qemu.org/docs/master/system/devices/net.html ; https://www.qemu.org/docs/master/system/qemu-manpage.html ; https://developers.home-assistant.io/docs/operating-system/partition/ .

## Supervisor supportability — documented source versus unverified guest

- Supervisor **2026.10.1** source `config.py` sets `APPS_LOCAL=apps/local` and `APPS_DATA=apps/data`. `bootstrap.py` conditionally moves legacy `addons/local` to `apps/local`, only when target absent. `store/data.py` finds `**/config.*` beneath `path_apps_local`, validates schema and prefixes the slug with `local_`. These are version-specific published source facts; the **actual running version inside HAOS 18.3** remains unknown.
- Source packaging: pinned HA-MCP 8.6.0 add-on has `config.yaml` with `image: ghcr.io/...`; the existing future runner strips `image:` and rewrites the Dockerfile path for local builds. No genuine Supervisor image/option persistence is verified.
- The guest test uses `/store/reload`, `/store`, `/store/addons/{slug}/install`, `/addons/{slug}/options`, `/addons/{slug}/start`; an API reply **alone** does not prove installed image and strict security. Version-specific route, role, schema and resulting image digest must be checked against actual Supervisor.
- The current harness seeds `supervisor/addons/local` *and* directly writes `supervisor/addons/data/.../tool_policy.json` to an offline guest disk. Even with correct `hassos-data` label, **direct internal data seeding is not established as a supported install or recovery mechanism**. It may bypass Supervisor's provisioning/migration and invalidates claims of tested user-facing recovery.
- **Smallest supported-direction correction:** prepare a local add-on tree matching current `apps/local`, verify signed/pinned file hashes, then have an authenticated *guest-local* Supervisor manage store refresh, install and options. For initial policy file use a separately reviewed, supported guest-local admin/restore mechanism; do NOT silently inject root-owned `/data` state. Record rollback to original image+configuration via actual Supervisor, not just Git reversal. Exact procedures must be proven in a future guest, not inferred from offline fixtures.

## Cleanup / diagnostic adversarial review (not independent sign-off)

1. Existing runner partially constructs firewall rules and attempts cleanup, but individual independent chain/ACL/NBD removal proofs are incomplete. It records only a subset of 13 desired cleanup conditions. Unknown read-back must be **not verified**, never success; cleanup failures should affect final exit.
2. Test guest currently sets `return 6` after partial tests, independent of optimistic messages; this prevents false-green today. The pure 16-gate model must be connected only to actual runtime observations by future reviewed code, **not** a mock-to-production switch.
3. `boot_wait()` accepts any HTTP 200 `/manifest.json` and its single diagnostic is merely the final observed port; it does not independently prove kernel/HAOS boot nor properly separate every observed stage.
4. `test_addon()` can report progress after Supervisor API requests without proof of actual backend security, starts, watchguard or installed image digest. All such cases remain NOT_TESTED.
5. Raw serial/HTTP bodies/secrets must not reach stdout, exception messages, GitHub artifacts, or review notes. Use fixed codes only; cap path/log reads and TTL; no unbounded retry.
6. Synthetic accepted sources `runtime_verified=True` are *assertions from the caller*, not cryptographic guest attestations. Full 16-pass simulation in unit tests **cannot** be treated as successful real Supervisor acceptance.
7. The separate AI review failed due to quota; this review is from the same implementation agent and does **NOT** constitute independent qualified security sign-off.
